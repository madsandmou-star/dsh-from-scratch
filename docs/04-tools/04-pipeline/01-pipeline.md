# 4.4 执行前后：把重复的护栏提出来

> 本课目标：把"执行一个工具"从一行 `await tool.execute()` 变成一条三段管线，并让权限、超时、截断、记账各自成为一层可插拔的护栏。这是 dsh 那条三段事件管线的手工版。

## 先看现在有多难受

六个工具之后，盘点一下：

| 关注点 | 现状 |
|---|---|
| 超时 | **只有 bash 有**。glob 在一棵大树上、grep 在一个大仓库里，都能跑到天荒地老 |
| 输出上限 | 三套：read 的 50KB、bash 的末尾 30KB、grep 的 100 条 × 300 字符 |
| 权限 | **一个都没有**（4.2 那个洞） |
| 耗时/开销 | 完全看不见。agent 变慢变贵时，你不知道是哪个工具干的 |

关键在于：**这四件事没有一件属于某个具体工具。** 它们是横切的——每加一个工具就要重新想一遍，还很容易漏（我们已经漏了五个工具的超时）。

把它们塞进每个工具里，是四份重复；塞进 `跑一个turn()` 里，是把 agent 循环变成一个什么都管的大函数。**正确的位置是两者之间：一条所有工具都要走的管线。**

## 三段：执行前 / 执行 / 执行后

```ts
export async function 执行工具(名字, 参数JSON, 护栏们, 超时毫秒): Promise<string>
```

流程是：找工具 → 解析参数 → **执行前**（放行/拒绝）→ **执行**（带超时和取消）→ **执行后**（加工结果）。

为什么正好是这三段？因为不同的关注点关心的是不同的**时刻**：

- 权限关心**执行之前**——该不该让它跑
- 超时关心**执行期间**——它必须能**环绕**执行，光在前面或后面挂钩子都做不到
- 记账、截断、日志关心**执行之后**——花了多久、产了多大、要不要改写

中间那段是"环绕"而不是"之间"，这一点最容易做错。超时不是"执行前设个闹钟、执行后关掉"，而是**必须持有那次执行本身**才能中止它。

```ts
export interface 护栏 {
  名字: string
  执行前?(上下文: 执行上下文): Promise<执行前决定> | 执行前决定
  执行后?(上下文: 执行上下文, 结果: string): Promise<string> | string
}
```

三个钩子都是可选的，每层只挂自己关心的那个。装配写在一个数组里：

```ts
const 护栏们 = [记账(config.记账), 只读模式(config.只读), 输出兜底()]
```

**换一套护栏不用改任何工具，也不用改 agent 循环。** 这就是抽出来的全部意义。

## 规矩一：执行前，失败即拒绝

```ts
try {
  决定 = await 一层.执行前(上下文)
} catch (错误) {
  return { 放行: false, 理由: `护栏「${一层.名字}」自己出错了：${...}` }
}
```

```
── ⑥ 护栏自己出错 → 失败即拒绝 ──
错误：护栏「坏掉的护栏」自己出错了：我自己炸了
```

一个护栏自己抛异常，结果必须是**拒绝**，不能是放行。理由很直接：**护栏坏掉的时候，"什么都不拦"是最糟的那个结果**。

dsh 把这条写得更狠。它的 `tools/pre-execute` 有三档决定：allow / deny / **ask**（问用户）。而 JSDoc 里明说：

> `next()` delegates to allow; **missing approval support turns `ask` into denial.**

也就是说：如果这套装配里根本没装审批插件，那么"我想问一下用户"这个回答会被解释成**拒绝**，而不是"没人能问，那就放行吧"。**当一个安全判断没法完成时，默认答案是不。** 这条规矩的名字叫 fail-closed，权限、锁、鉴权都适用。

## 规矩二：执行后，失败即忽略

```
── ⑦ 执行后钩子出错 → 结果照常返回 ──
[护栏 坏掉的记账 的执行后钩子出错，已忽略] 记账炸了
   1: hello
```

执行后**反过来**：一层挂了，只记一句日志，结果照常往下走。

因为结果**已经产生了**——文件已经写了、命令已经跑了。这时候因为一个记账钩子出错就把结果吃掉，等于让模型以为操作失败了，而它其实成功了。**那比丢掉一条日志危险得多。**

dsh 同样的分法：`tools/result` 那一档的 JSDoc 写着 `Listener failures are contained.`（监听器的失败被隔离）。

**同一个"钩子抛异常了怎么办"，在管线的两端答案相反。** 判据不是"该不该容错"，而是：**这一步失败，是让世界少发生一件事，还是让已经发生的事被误报？**

## 规矩三：谁施加的限制，谁负责解释

统一超时第一次跑出来是这样的：

```
── ④ 统一超时：bash 睡 10 秒，上限 1 秒 ──
(没有输出)
[被信号杀掉：SIGKILL]
```

**这对模型来说是一句没头没脑的话。** 它不知道是谁杀的、为什么杀、要不要重试。

原因是取消在 Node 里是**合作式**的：`signal` 一响，工具怎么反应由它自己决定。bash 收到信号后杀掉子进程，然后**正常返回**了一个"被 SIGKILL 了"的结果——从它自己的角度看，这次执行结束得很正常。

所以管线要补一句：

```ts
if (控制器.signal.aborted) {
  结果 = `错误：工具 ${名字} 超过了 ${超时毫秒}ms 的时间上限，已被中止。\n[中止前拿到的输出]\n${结果}`
}
```

```
错误：工具 bash 超过了 1000ms 的时间上限，已被中止。
[中止前拿到的输出]
(没有输出)
[被信号杀掉：SIGKILL]
```

**限制是管线施加的，那么解释就是管线的责任。** 顺便保留了中止前的部分输出——那可能正是模型需要的线索（比如一个测试跑到一半的日志）。

dsh 在这里做得更严密：`tools/execute` 的环绕包装器**只允许改 `exec.signal` 这一样东西**，而且注册表在真正调用工具之前会把**原来那个调用方的信号重新熔进去**：

> wrappers may change only `exec.signal` … The registry re-fuses the original caller signal before the body, so replacement cannot detach caller cancellation.

翻译过来：一个超时包装器可以把自己的超时信号叠上去，但**没法把用户按 Ctrl-C 的那个信号顶掉**。否则你会得到一个"超时能中止、但用户中止不了"的 agent。

## 规矩四：两层超时，两个问题

bash 现在有两个超时，这不是重复：

| | 谁的 | 回答的问题 | 默认 |
|---|---|---|---|
| `timeout_ms` | bash 工具自己的 | 一条命令跑多久算久 | 30 秒 |
| 管线超时 | 所有工具共用的 | 任何工具都不许卡住整个 agent | 60 秒 |

前者模型可以调（"这次 npm install 慢，给我 5 分钟"）；后者是装配的底线，模型碰不到。**一个是业务预算，一个是系统底线。**

dsh 也是这两层：shell 的 `timeoutMs` 在提供者（`bash-local`）里，`dsh-tool-call-timeout-policy` 是挂在 `tools/execute` 上的一个环绕包装器。**两层分别属于两个包**，因为它们回答的是两个问题。

bash 现在同时接两个信号：

```ts
const 被外层中止 = () => { 子进程.kill('SIGKILL') }
signal.addEventListener('abort', 被外层中止, { once: true })
...
子进程.on('close', () => {
  clearTimeout(定时器)
  signal.removeEventListener('abort', 被外层中止)   // ← 这一行不能少
  ...
})
```

**移除监听器那一行不是洁癖。** `signal` 的生命周期可能比这次调用长；不摘掉的话，每次调用都往上挂一个闭包，闭包又抓着子进程对象——这是 Node 里最常见的一类内存泄漏。**注册和注销要成对，而且注销要放在必然会执行的那条路径上。**

> **顺带一个真实事故**：给 `Tool.execute` 加上第二个参数 `signal` 之后，`demos/` 里所有**直接调 `tool.execute(args)`** 的脚本全炸了——`signal` 是 `undefined`，bash 一上来就 `Cannot read properties of undefined (reading 'addEventListener')`。JS 不检查参数个数，所以这些错只在运行时才冒出来。
>
> 这件事本身就是一个论据：**除了演示，任何地方都不该直接调 `execute()`，而应该走管线。** dsh 更彻底——工具的 `execute` 根本不是公开 API，外面只能通过注册表去派发，护栏因此**没法被绕过**。

## 插曲：两个人同时想喊停

上面那句"注册表重熔调用方信号"值得单独展开，因为它是这条管线里**唯一一个我们没做、但真实产品必须做**的东西。

先把两个词说清楚。

**"环绕"就是 Python 的装饰器。** 一个包装器手里握着"调用原函数"这个动作本身，所以它可以选择不调、调完改结果、或者在调用期间盯着它。我们管线里那三行 `setTimeout` / `await execute` / `clearTimeout` 就是写死的环绕；dsh 的区别是这个位置**对插件开放**，就像给一个函数叠多个装饰器。

**`AbortSignal` 就是一个遥控停止按钮**，分两半：`AbortController` 是**按钮**（`abort('理由')`），`controller.signal` 是**接收器**，交给干活的人自己盯着。注意它是**合作式**的——Node 不会替你掐掉任何东西，是干活的人**答应了**要盯着这个按钮。他不盯，按了也没用（4.3 的 ReDoS 就是没人盯的情况）。

麻烦在于：一次工具调用，**同时有两个人想按停止按钮**——用户（Ctrl-C）和超时包装器。而 `execute(args, signal)` **只收一个 signal**。

包装器要加自己的超时，最自然的写法就是造一个自己的 controller 塞进去。问题就在这：**用户那个被顶掉了。**

`demos/04-tools/11-signal-fusion.mjs` 把这件事跑出来。工具本来要跑 5 秒，用户在 500ms 按 Ctrl-C，超时设在 3 秒：

```
=== 场景 A：包装器直接把 signal 换成自己的 ===
  被打断了：超时 3 秒（等了 3004ms）
  用户那个按钮按了吗？ 按了，但没人在听

=== 场景 B：注册表把两个熔在一起 ===
  被打断了：用户按了 Ctrl-C（等了 500ms）
```

**场景 A 里用户按了停止，然后干等了 3 秒。** 从他的角度看：这个 agent 的停止按钮坏了。

这个 bug 极其阴，因为它**只有在同时存在两个取消源时才出现**。你单独测超时，好使；在没装超时插件的装配里单独测 Ctrl-C，也好使。两个一起才炸。

dsh 的解法是：**包装器怎么改都行，但在真正调用工具之前，注册表把调用方那个 signal 再焊回去。**

```ts
const wrapperSignal = exec.signal                                 // 包装器留下的
const fused = fuseToolSignals(state.callerSignal, wrapperSignal)  // 和调用方的熔在一起
exec.signal = fused.signal                                        // 工具拿到的是熔合后的
try { await tool.execute(exec.arguments, exec) }
finally { fused.dispose(); exec.signal = wrapperSignal }           // 用完还原
```

"熔合"就是标准库 `AbortSignal.any([甲, 乙])` 的意思——**这两个里任何一个响了，我就响**。dsh 手写了一个等价的 `fuseToolSignals()`，多做了三件事：保住 `reason`（好区分"是谁按的"）、用完 `dispose()` 摘掉监听器（4.4 前面讲过的那类泄漏）、以及在 `caller === wrapper` 时直接短路不熔。

注意注册表**并不禁止**包装器换 signal——换是正当需求。它只是在最后一刻**加回来**，所以包装器**没办法**把调用方的取消权拿掉，哪怕它想。这也是为什么规则写成"只准改 `exec.signal` 这一样东西"：换 signal 是唯一有正当理由的改动，而这一样又被兜住了；工具名、参数、调用身份全部只读。

**为什么要在协议里写死，而不是要求写包装器的人小心点？** 因为这不是一个人的事：挂在这一段上的可能有超时插件、重试插件、埋点插件，三个不同作者、三个包。只要**其中一个**忘了带上调用方的 signal，整个 agent 的 Ctrl-C 就失效，而且没人知道是谁弄的。

**把保证放进注册表，就是把"每个插件作者都得记得"变成"没人能搞错"。** 这和 4.3 那条"能不引入解释器就别引入"是同一种思路：不要求每个人都写对，而是让**写错这件事本身不可能发生**。

> 我们的管线目前只有一个取消源（管线自己的超时），所以还撞不上这个问题。阶段 13 加用户取消之后就会——**到时候记得回来看这一节**。

## 规矩五：通用护栏是兜底，不是替代品

```ts
执行后(上下文, 结果) {
  if (结果.length <= 输出兜底上限) return 结果
  return `${结果.slice(0, 输出兜底上限)}\n\n[${上下文.工具名} 的输出超过 ${输出兜底上限} 字符，已由统一护栏截断]`
}
```

有了这一层，能不能把 read / bash / grep 各自的截断删掉？**不能。**

那三处截断都是**懂行的**：read 保留开头、bash 保留末尾、grep 逐行裁并告诉模型总共匹配了多少处。统一护栏什么都不懂，它只会从中间一刀切下去。

所以现有六个工具都不会触发它——它保护的是**你还没写的那个工具**，或者某天有人漏了截断的那个：

```
── ⑤ 执行后兜底：一个忘了自己截断的工具 ──
[记账] 没截断的工具 耗时 0ms，输出 200000 字符
xxxxxxxx…（共 60034 字符）
```

顺带看一眼记账那行：它报的是 **200000**，因为 `记账` 在数组里排在 `输出兜底` 前面，看到的是**没被截断的原始输出**。这正是记账想要的——你要知道工具**真的**产了多少，而不是截断后剩多少。**执行后钩子的顺序决定每一层看到什么**，这是排列数组时要想清楚的事。

## 权限的座位已经留好了

只读模式是这一课唯一一个真的"权限"，但它已经足以说明形状：

```
==================== 只读 = false ====================
  [工具] edit(...)   → 已修改 add.mjs（替换了 14 字符 → 14 字符）
模型 > 改好了。
--- add.mjs 现在 ---  return a + b

==================== 只读 = true ====================
  [工具] edit(...)   → 错误：被护栏「只读模式」拒绝：当前是只读模式，edit 不能用。
                        你可以用 read / glob / grep 查看，但不能修改任何东西。
模型 > 我只能看不能改，这里应该把减号换成加号。
--- add.mjs 现在 ---  return a - b
```

**同一个 agent、同一套工具、同一段模型输出，只改配置里一个开关。** 而且注意拒绝理由那句话是写给模型的：它告诉模型**还剩什么能用**，所以模型没有崩溃也没有反复重试，而是换了个交付方式——把改法说出来。

这也是为什么它是**配置字段**而不是常量：同一份代码，装在 CI 里做代码审查时要只读，装在你自己机器上改代码时不要。AGENTS.md 那条「插件里不许有硬编码的可调参数」，这里是第二次用上（第一次是 4.2 的超时）。

dsh 里对应的东西叫 **plan 模式**，是一整个包（`dsh/packages/plan/`），而且做得比我们彻底：它是**被记进会话日志的状态**，不是一个进程内的布尔值。为什么必须进日志？因为「**模型可见 ⟺ 已落日志**」——模型知道自己在 plan 模式（这影响它怎么回答），那么重放这个会话时就必须能重建出这个事实。阶段 6 讲会话落盘时会正面处理这条规矩。

至于真正的"问用户"式审批，阶段 15 才做。但**座位已经在这里了**：它就是又一个 `执行前` 钩子。

## 一个我们补不掉的洞，再确认一次

4.3 说过：ReDoS 的洞，统一超时救不了。现在管线有超时了，实测一次：

```
管线超时设成 1000ms，跑 grep (a+)+$ …
[退出码 124 —— 124 表示 10 秒后仍未返回]
```

**超时设了 1 秒，10 秒后还没回来。** 因为 `setTimeout` 要等事件循环，而正则把事件循环占死了——`控制器.abort()` 那行代码根本没机会执行。

**这不是管线设计得不好，是"在同一个线程里做超时"这件事的物理上限。** 出路只有两条，都是把工作挪出这个线程：换个不回溯的引擎（ripgrep）、或者塞进子进程/worker（这样 SIGKILL 才有意义）。dsh 两条都占了。

**知道自己的机制在哪里失效，和有这个机制一样重要。**

## 对照 dsh

我们这条管线是 `dsh/packages/core/tools/src/index.ts` 的手工版。对照表：

| | 我们的 | dsh |
|---|---|---|
| 三段 | 数组里按顺序调函数 | 三个 **waterfall 事件**：`tools/pre-execute` / `tools/execute` / `tools/post-execute` |
| 谁来挂 | `index.ts` 里写死的数组 | 任何插件 `ctx.on('tools/pre-execute', ...)`，**可动态装卸** |
| 执行前决定 | 放行 / 拒绝 | allow / deny / **ask**（无审批能力时 ask ⇒ deny） |
| 环绕 | 管线自己的 `setTimeout`（唯一取消源） | `tools/execute` 包装器，**只能改 `exec.signal`**，注册表把调用方信号熔回去（见上面那节插曲） |
| 执行后 | 只能改文本 | accept / **replace** / enrich / block；**抛错的工具也会走到这一档** |
| 顺序保证 | 靠数组 | `invariant.ts` 在运行时**断言**：pre 必须先于 execute，execute 必须先于 post，pre 对同一次执行不许重复 |
| 最终观察 | 无 | `tools/result`（emit）：拿到深冻结的最终结果，监听器失败被隔离 |

三处值得展开：

**① 为什么是 waterfall 而不是普通事件。** 阶段 10 会正面讲，这里先看形状：waterfall 的每个监听器都拿到一个 `next()`，**调 `next()` 就是"我没意见，交给下一个"**，不调就是"我说了算，到此为止"。我们那个 for 循环里的 `if (!决定.放行) return` 就是最朴素的短路版本。dsh 的 AGENTS.md 里有一条硬规矩：「**waterfall 监听器必须调 `next()` 来委托；不调就直接返回等于短路整条链**」——写错这一行，后面所有插件就静悄悄地失效了。

**② 运行时断言顺序。** `invariant.ts` 里那几行很有意思：

```
if (stages.has(exec)) fail('tools/pre-execute repeated for one execution')
if (stages.get(exec) !== 'pre') fail('tools/execute must follow tools/pre-execute')
```

它不检查"有没有这个服务"或者"插件注册了没有"，而是检查**真实发生的事件流之间的关系**。这正是 AGENTS.md 那条「运行时不变量断言的是**自己拥有的关系**，检查权威事件流或可变数据，而不是服务或方法存不存在」。翻译成人话：**别测试"我导出了这个函数"，要测试"这两件事的先后顺序确实成立"。**

**③ 抛错的工具也走 post-execute。** 我们的管线也做到了这一点——被拒绝、超时、工具自己抛错，全都变成文本之后**继续走执行后钩子**。这不是顺手，是必需的：失败也是结果，截断和记账对它一样适用，而且失败的结果往往**更**需要被记账（你想知道哪个工具老是失败）。
