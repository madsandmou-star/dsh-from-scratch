# 2.1 流式是什么：SSE 分帧

> 本课目标：看清"加一个 `stream: true` 之后，响应到底变成了什么"，以及它为什么不只是体验优化。

## 痛点：按下回车之后的十几秒

阶段 1 的 agent 有个说不出的难受：你输入一句话，屏幕上**什么都没有**，等一会儿"啪"地出来一整段。

用户分不清程序是在思考还是卡死了。实测同一个请求的两种模式：

```
非流式：  1532ms 才拿到全部内容（在这之前屏幕一片空白）

流式：     179ms  agent
           380ms  是能
           581ms  自己调用
           782ms  工具
           983ms  去完成
          1184ms  任务的
          1385ms  程序。
```

**总时长几乎一样**（1385ms vs 1532ms），但第一个字出现的时间从 1.5 秒变成 0.18 秒——**快了 8 倍**。用户感知里这是两个产品。

## 解法：一句话和一张图

**别等模型把话说完再要——改成 `stream: true`，供应商会用 SSE 一小段一小段地推过来，我们收到一段就上一段屏。**

```
非流式（1.3 那样）：
  请求 ──────────── 等 12 秒 ────────────→ 一整段回复
  屏幕：                                  什么都没有 …… 然后"啪"地全出来

流式：
  请求 ─→ data: {"delta":{"content":"agent"}}   ─→ 屏幕：agent
       ─→ data: {"delta":{"content":" 是"}}      ─→ 屏幕：agent 是
       ─→ data: {"delta":{"content":"能"}}       ─→ 屏幕：agent 是能
       ─→ data: [DONE]                           ─→ 结束
```

### 请求端只改一个字段

```jsonc
{ "model": "deepseek-chat", "messages": [ ... ], "stream": true }
```

### 响应端换了一种协议

不再是一个 JSON 对象，而是一串 **SSE 事件**：每条以 `data: ` 开头，事件之间用**一个空行**隔开，最后一条固定是 `data: [DONE]`。

```
data: {"choices":[{"index":0,"delta":{"content":"agent"},"finish_reason":null}]}

data: {"choices":[{"index":0,"delta":{"content":" 是"},"finish_reason":null}]}

data: [DONE]

```

### 代价

这一个字段换来的不是"一行代码的改动"，而是三件事从此都得自己管：**怎么把字节流切成事件**（2.2）、**怎么把增量拼成完整文本**（2.3）、以及**流中途断了算什么**（2.3 / 2.4）。

这一课先把线上的东西看清楚：`delta` 和 `message` 的区别、`[DONE]` 缺失意味着什么。下面逐条看。

## 线上到底传了什么

请求只多一个字段：

```jsonc
{ "model": "...", "messages": [...], "stream": true }
```

响应的 `content-type` 变了：

```
HTTP/1.1 200 OK
content-type: text/event-stream     ← 不再是 application/json
cache-control: no-cache
```

`text/event-stream` 是 **SSE**（Server-Sent Events）：一条长连接，服务器持续往里写"事件"，客户端边收边处理。

原始字节长这样（`⏎` 是换行）：

```
data: {"choices":[{"index":0,"delta":{"content":"agent "},"finish_reason":null}]}⏎
⏎
data: {"choices":[{"index":0,"delta":{"content":"是能"},"finish_reason":null}]}⏎
⏎
```

三件事要记住：

1. **每个事件以 `data: ` 开头**，后面跟一行 JSON。
2. **每个事件以一个空行结束**——也就是 `\n\n`。这个空行是**分帧符**：没有它，接收方不知道一个事件结束没有。
3. 最后一个事件是固定的 `data: [DONE]`，然后连接关闭。

> 这是 SSE 规范的一部分，不是 OpenAI 发明的。规范还允许 `event:`、`id:`、`retry:` 字段和 `:` 开头的注释行——聊天补全接口只用到 `data:`。

## `delta` 不是 `message`

对比阶段 1 的非流式响应：

```jsonc
// 非流式：一个完整快照
"message": { "role": "assistant", "content": "agent 是能自己调用工具去完成任务的程序。" }

// 流式：一串增量
"delta": { "content": "agent " }
"delta": { "content": "是能" }
"delta": { "content": "自己调用" }
```

**流式给的是增量（delta），不是快照。** 完整文本要你自己拼。这条差异会在阶段 3 变得很烦：工具调用的参数也是分块到达的，你得按 index 把 JSON 字符串一片片拼起来，拼完才能 `JSON.parse`。

倒数第二个事件带 `finish_reason`，`delta` 是空的：

```jsonc
{"choices":[{"index":0,"delta":{},"finish_reason":"stop"}]}
```

1.2 讲过的 `stop` / `length` / `tool_calls` 在流式里是这样出现的——**它单独占一帧**，不跟着内容走。

## `[DONE]` 缺失意味着什么

正常结束是：最后一帧 `data: [DONE]`，然后连接关闭。

如果连接关掉了却**没有** `[DONE]`，说明这次响应是**被截断的**——网络断了、服务器崩了、代理超时了。此时你手里有半段文本。

关键问题：**半段文本能用吗？**

不能。它可能停在半句话、半个 JSON 参数、半个工具调用上。把它当成完整回复写进历史，下一轮模型会看到一段莫名其妙的残句。

dsh 的处理是明确的（`dsh/packages/llm/llm-deepseek/src/sse.ts`）：**流在 `[DONE]` 之前结束就抛 `LlmError('STREAM_CLOSED')`**，注释里写着"截断——这次模型调用不可信"。

> 这是"半成品状态"这个主题的第二次出现。1.4 是"失败留下悬空消息"，这里是"断流留下半句话"。第三次会在阶段 3（工具执行到一半），第四次在阶段 12 给出统一答案。

## 教 debug：管道缓冲会骗你

```sh
curl -N ...     # -N / --no-buffer：禁用 curl 自己的输出缓冲
```

不加 `-N` 的时候，curl 可能攒够一块才输出，你会**误以为服务器是一次性返回的**——明明是流式，看起来却像非流式。

同样的陷阱在管道里也有：`curl ... | grep foo` 时 grep 也会缓冲。想看真实到达时刻，要么直接输出到终端，要么像本课那样给每行打时间戳。

**排查流式问题的第一步永远是：确认你看到的延迟是真实的，还是被某一层缓冲伪造的。**

## 对照 dsh：分帧这件事它不自己写

我们下一课会手写一个分帧器（缓冲 + 按 `\n\n` 切）。dsh 不写——它用 `eventsource-parser` 这个库，`sse.ts` 的模块注释把边界划得很清楚：

> 分帧——chunk 重组、UTF-8/CRLF/BOM 处理、注释与非 data 字段跳过、多个 `data:` 的拼接——是 `eventsource-parser` 的职责。这个模块只保留 DeepSeek 的协议部分：字面量 `[DONE]` 会被原样 yield 出去让调用方决定何时收尾，而在它之前遇到 EOF 则抛 `LlmError`。

这是那条"**优先选用持续维护的依赖，而非手写实现**"规矩的一次具体应用：SSE 分帧看起来简单，实际有一堆边界情况（CRLF、BOM、多行 data、注释行、UTF-8 被切开）。手写一遍你会懂，但产品代码里让库来做。

注释最后一句还点了一个细节：**分帧严格遵守规范——事件只在遇到空行终止符时才派发**，所以 EOF 时那截没终止的尾巴是"截断"，不是"可以冲刷出来的数据"。
