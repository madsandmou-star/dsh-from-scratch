# 2.3 接进对话循环

> 本课目标：把分帧器接进 `chat()`，并看清一个签名改动是怎么向上传染的。

## 一个改动，两处传染

`chat()` 的返回值从"一个字符串"变成"一串增量"。改完 `llm.ts` 后跑类型检查，编译器立刻指出传染点：

```
src/index.ts(11,10): error TS2305: Module '"./llm.ts"' has no exported member 'chat'.
```

**这就是类型系统真正值钱的地方**（0.2 讲过）：它不保证你的逻辑对，但它保证你改了一处之后，所有受影响的地方都会亮红灯。

## 设计选择：异步生成器 vs 回调

两种写法都能实现流式：

```ts
// A. 回调
chatStream(messages, config, delta => process.stdout.write(delta))

// B. 异步生成器
for await (const delta of chatStream(messages, config)) process.stdout.write(delta)
```

我们选 B，理由有三条：

1. **控制流是平铺的**。回调把"发请求"和"处理增量"拆到两个地方，读代码要来回跳。
2. **背压是自动的**。调用方处理得慢，生成器就停在 `yield` 那里等它——`for await` 天然是拉取模型。回调是推送模型，处理不过来只能自己排队。
3. **提前停止不需要额外约定**。调用方 `break`，生成器的 `finally` 就会执行，连接自然收尾。回调写法得发明一个"返回 false 表示停止"的约定，而且每个调用方都要记得遵守。

> 阶段 3 加工具调用时第 3 条会兑现：工具调用一旦成形就可以提前中断本次流。

`llm.ts` 的实现是 `async function*`——函数名前的 `*` 表示生成器，函数体里的 `yield` 产出一个值。Python 的 `async def` + `yield` 是同一件事，`for await ... of` 对应 `async for`。

## 调用方的三处变化

看 [`src/index.ts`](../../../src/index.ts) 改动后的循环：

```ts
process.stdout.write('\n模型 > ')
let reply = ''
for await (const delta of chatStream(messages, config)) {
  process.stdout.write(delta)     // ① 逐字上屏，不换行
  reply += delta                  // ② 同时自己攒完整文本
}
messages.push({ role: 'assistant', content: reply })
```

1. **没有"拿到回复"这个时刻了**。以前 `const reply = await chat(...)` 一行搞定，现在打印和累积同时发生。
2. **"完整回复"要自己攒**。历史里要存的是完整文本，而流式只给增量——**攒出来的东西才能进历史**。
3. **`process.stdout.write` 而不是 `console.log`**：后者每次都换行，打字机效果会变成竖着的一列字。

实测（每行前面是到达时刻）：

```
[1095ms] "\n模型 > "
[1378ms] "agent "
[1571ms] "是能"
[1770ms] "自己调用"
[1971ms] "工具"
[2172ms] "去完成"
[2373ms] "任务的"
[2574ms] "程序。"
```

## 断流：屏幕上已经有半句话了

这是流式带来的新问题，非流式时代不存在：**失败时用户已经看到内容了，收不回来。**

两种断法要分清，实测两条都走通了：

```sh
# ① 连接被掐（服务器 destroy、网络断、代理超时）
模型 > 这句话说到一半就断
[本轮中断，已丢弃] terminated                    ← fetch 底层抛的

# ② 干净地结束，但没发 [DONE]
模型 > 看起来正常结束了
[本轮中断，已丢弃] 流在收到 [DONE] 之前就结束了：这次回复不完整，不可信
```

第 ② 种阴险得多：**HTTP 层面一切正常，200、连接干净关闭**。只有协议层的 `[DONE]` 缺失能告诉你这次回复被截断了。如果不检查，你会把"看起来正常结束了"当成完整回复写进历史。

我们的处理是**不把半句话写进历史**：给用户一个明确的中断标记，撤回这一轮的 user 消息。

理由和 2.2 丢弃未终止残片完全一样——**残缺内容一旦进了历史，下一轮模型会拿它当事实**。屏幕上留着那半句话是可以接受的（用户看见了中断标记，知道发生了什么），但历史必须干净。

> **半成品状态，第四次出现。** 前三次：1.4 悬空 user 消息、2.1 缺 `[DONE]`、2.2 未终止残片。
>
> 注意这一次比前三次更难：前三次是"要不要保留一段数据"，这一次**屏幕上的字已经泼出去了**。我们只能保证历史干净，没法保证用户没看见。阶段 12 之后你会发现这个区分有名字：**已提交的事实**和**未提交的中间态**。

## 教 debug：区分"没收到"和"收到了但没显示"

流式出问题时第一个要回答的问题是：**增量到底有没有到？**

```ts
for await (const payload of parseSse(response.body)) {
  console.error(`[SSE] ${payload.slice(0, 80)}`)     // 注意用 stderr
  ...
}
```

用 `console.error`（stderr）而不是 `console.log`——因为 stdout 正在被打字机效果占用，混在一起没法看。想只看调试信息就 `node ... 2>&1 >/dev/null`，想只看正常输出就 `2>/dev/null`。

**把诊断输出和产品输出分到不同的流，是 CLI 程序的基本功。** dsh 对这条更严格：agent-spine 里连 `timer` 插件都被特意注明"不往 stdout 写任何东西"，因为 stdout 是 ACP/JSON-RPC 的协议通道，混进一个字节整个协议就废了。
