## 对照 dsh：同一件事由谁来做

我们四个文件干的活，在 dsh 里散落在这些地方：

| 我们的 | dsh 的 | 差在哪 |
|---|---|---|
| `config.ts` 读 JSON | `dsh/packages/credentials/`（密钥来源 seam）+ 各插件的 Schemastery config | 配置是插件树的一部分，可分层覆盖；密钥来源可替换 |
| `types.ts` 的 `Message` | `dsh/packages/llm/llm/src/message.ts` 的内部消息词汇 | 内部表示不等于某家供应商的 wire 格式，中间隔一层翻译 |
| `llm.ts` 的 `chat()` | `dsh/packages/llm/llm-deepseek/src/`（adapter / serialize / translate / sse） | 流式、分类错误、重试、图片、思维链 |
| `index.ts` 的 while 循环 | `dsh/packages/core/agent-loop/src/agent.ts` | 工具、turn/step、inbox、取消、持久化、事件 |
| —— | `dsh/packages/core/session/` | 我们的 `messages` 数组在 dsh 里是**从事件日志投影出来的**（阶段 12） |

一句话概括这张表：**dsh 把我们混在一起的四件事拆成了四条可替换的能力**。拆分本身是有代价的（更多文件、更多间接层），代价换来的是"换掉其中一件不影响其他三件"。这门课后面十几个阶段，就是一次一次地把这笔交易做给你看。

## 工程思维总结

### 1. 先裸写，再抽象

我们本可以一上来就用某个 SDK，三行搞定。但那样你不会知道：`fetch` 不为 4xx 抛错、`content` 可以是 `null`、`finish_reason` 有几种值、历史是客户端拼的。这些事实是后面所有设计决策的地基——**抽象是用来隐藏细节的，你得先见过细节，才知道它隐藏得对不对。**

反过来也成立：抽象要在**痛点出现之后**引入。现在只有一个入口、一个供应商、一种消息类型，此刻引入 provider 抽象层是纯粹的成本。

### 2. 错误信息是给卡住的人写的

`throw new Error('配置错误')` 和 `throw new Error('环境变量 DEEPSEEK_API_KEY 没有设置。\n先导出密钥：export DEEPSEEK_API_KEY=sk-...')` 的代码成本差不多，帮助差一个数量级。

判断标准：**读到这条消息的人，能不能不用去读源码就知道下一步该做什么。**

### 3. 状态是 bug 的温床

这一阶段唯一真正的坑是"请求失败后 `messages` 里留了半条消息"。它很小，但它是后面一大类问题的原型：任何"一个操作改了多处状态，中途失败"的地方都会长出同样的 bug。

工业级的答案不是"每处都记得回滚"，而是**换一种状态表示，让半成品根本不存在**——追加式日志（阶段 12）、可逆的注册（阶段 9）都是这个思路。记住这个疼，到时候你会认出它。

## 下一阶段的痛点预告

现在的体验有个明显的难受之处：**按下回车之后，屏幕上什么都没有，要等十几秒才"啪"地出来一整段。**

用户不知道程序是在思考还是卡死了。解决它需要把"等全部生成完"改成"边生成边打印"——听起来只是体验优化，实际上会把 `chat()` 的返回值从"一个字符串"变成"一串增量"，而这个改变会一路影响到工具调用（参数是分块到达的）、UI（要能实时渲染）、持久化（原始增量要留档才能重放）。

dsh 索性把流式当成默认而不是选项。下一阶段你就会明白为什么。
